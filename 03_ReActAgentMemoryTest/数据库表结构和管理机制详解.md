# LangGraph 数据库表结构和管理机制详解

## 一、数据库表结构总览

LangGraph 的 `AsyncPostgresSaver` 和 `AsyncPostgresStore` 会在 PostgreSQL 数据库中自动创建以下表：

### 短期记忆（Short-term Memory）相关表

1. **checkpoints** - 检查点主表
2. **checkpoint_writes** - 检查点写入表（存储实际数据）
3. **checkpoint_blobs** - 检查点二进制大对象表
4. **checkpoint_migrations** - 检查点数据库迁移版本表

### 长期记忆（Long-term Memory）相关表

5. **store** - 长期记忆存储表
6. **store_migrations** - 长期记忆数据库迁移版本表

---

## 二、表结构详细说明

### 2.1 checkpoints 表（检查点主表）

**用途**：存储每个检查点的元数据和状态信息

**表结构**：
```sql
CREATE TABLE checkpoints (
    thread_id            TEXT NOT NULL,           -- 会话/线程ID，用于区分不同的对话会话
    checkpoint_ns        TEXT NOT NULL DEFAULT '', -- 检查点命名空间
    checkpoint_id        TEXT NOT NULL,           -- 检查点唯一标识符（UUID格式）
    parent_checkpoint_id TEXT,                    -- 父检查点ID，用于构建检查点链
    type                 TEXT,                    -- 检查点类型
    checkpoint           JSONB NOT NULL,          -- 检查点元数据（JSON格式）
    metadata             JSONB NOT NULL DEFAULT '{}', -- 额外的元数据信息
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);

-- 索引
CREATE INDEX checkpoints_thread_id_idx ON checkpoints(thread_id);
```

**字段说明**：
- `thread_id`: 标识不同的对话会话，例如 "1"、"user_123" 等
- `checkpoint_id`: 每次 agent 执行时创建的检查点唯一ID（UUID格式）
- `parent_checkpoint_id`: 指向上一个检查点，形成检查点链，支持回溯历史状态
- `checkpoint`: JSONB格式，包含检查点的版本信息、时间戳、通道版本等元数据
- `metadata`: 存储额外的元数据信息

**示例数据**：
```
thread_id: "1"
checkpoint_id: "1f0b944b-831e-6d7e-800e-a4cb9f31a179"
parent_checkpoint_id: "1f0b944b-5418-6516-800d-a529cec20dae"
```

### 2.2 checkpoint_writes 表（检查点写入表）

**用途**：存储每个检查点的实际数据内容（消息、状态等）

**表结构**：
```sql
CREATE TABLE checkpoint_writes (
    thread_id     TEXT NOT NULL,           -- 会话ID
    checkpoint_ns TEXT NOT NULL DEFAULT '', -- 检查点命名空间
    checkpoint_id TEXT NOT NULL,           -- 检查点ID
    task_id       TEXT NOT NULL,           -- 任务ID（UUID格式）
    idx           INTEGER NOT NULL,         -- 索引，用于排序同一任务的多个写入
    channel       TEXT NOT NULL,           -- 频道名称（如 "messages", "llm_input_messages"）
    type          TEXT,                    -- 数据类型（如 "msgpack"）
    blob          BYTEA NOT NULL,          -- 二进制数据（序列化后的消息/状态）
    task_path     TEXT NOT NULL DEFAULT '', -- 任务路径
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id, task_id, idx)
);

-- 索引
CREATE INDEX checkpoint_writes_thread_id_idx ON checkpoint_writes(thread_id);
```

**字段说明**：
- `channel`: 标识数据类型
  - `messages`: 存储完整的对话消息列表（HumanMessage, AIMessage, ToolMessage等）
  - `llm_input_messages`: 存储经过修剪后输入给LLM的消息
  - `branch:to:agent`: 分支信息
  - `branch:to:pre_model_hook`: 分支信息
- `blob`: **二进制格式存储**（msgpack序列化），这就是为什么直接查询SQL看不到可读内容的原因
- `type`: 数据类型，常见值为 "msgpack" 或 null

**示例数据**：
```
thread_id: "1"
checkpoint_id: "1f0b944b-5418-6516-800d-a529cec20dae"
channel: "messages"
type: "msgpack"
blob_size: 1146 bytes  (二进制数据，无法直接读取)
```

### 2.3 checkpoint_blobs 表（检查点二进制大对象表）

**用途**：存储大型二进制对象，用于优化存储

**表结构**：
```sql
CREATE TABLE checkpoint_blobs (
    thread_id     TEXT NOT NULL,           -- 会话ID
    checkpoint_ns TEXT NOT NULL DEFAULT '', -- 检查点命名空间
    channel       TEXT NOT NULL,           -- 频道名称
    version       TEXT NOT NULL,           -- 版本号
    type          TEXT NOT NULL,           -- 数据类型
    blob          BYTEA,                   -- 二进制数据（可选）
    PRIMARY KEY (thread_id, checkpoint_ns, channel, version)
);

-- 索引
CREATE INDEX checkpoint_blobs_thread_id_idx ON checkpoint_blobs(thread_id);
```

### 2.4 checkpoint_migrations 表（迁移版本表）

**用途**：记录数据库schema的迁移版本

**表结构**：
```sql
CREATE TABLE checkpoint_migrations (
    v INTEGER NOT NULL PRIMARY KEY  -- 迁移版本号
);
```

### 2.5 store 表（长期记忆存储表）

**用途**：存储长期记忆数据（用户偏好、配置等）

**表结构**：
```sql
CREATE TABLE store (
    prefix      TEXT NOT NULL,                    -- 命名空间前缀（如 "memories"）
    key         TEXT NOT NULL,                    -- 存储键（UUID格式）
    value       JSONB NOT NULL,                   -- 存储值（JSON格式）
    created_at  TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP, -- 创建时间
    updated_at  TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP, -- 更新时间
    expires_at  TIMESTAMP WITH TIME ZONE,         -- 过期时间（可选）
    ttl_minutes INTEGER,                          -- 生存时间（分钟）
    PRIMARY KEY (prefix, key)
);

-- 索引
CREATE INDEX idx_store_expires_at ON store(expires_at) WHERE expires_at IS NOT NULL;
CREATE INDEX store_prefix_idx ON store(prefix text_pattern_ops);
```

**使用示例**：
```python
# 存储长期记忆
namespace = ("memories", "user_123")
await store.aput(namespace, "memory_id_1", {"data": "我的名字叫南哥"})

# 检索长期记忆
memories = await store.asearch(namespace, query="")
```

### 2.6 store_migrations 表（长期记忆迁移版本表）

**用途**：记录长期记忆存储的数据库schema迁移版本

**表结构**：
```sql
CREATE TABLE store_migrations (
    v INTEGER NOT NULL PRIMARY KEY  -- 迁移版本号
);
```

## 三、数据存储和管理机制

### 3.1 初始化流程

#### 3.1.1 短期记忆初始化

```python
# 01_shortTermTest.py
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

db_uri = "postgresql://postgres:sxl_pwd_123@localhost:5433/sxl_pg_db1?sslmode=disable"

async with AsyncPostgresSaver.from_conn_string(db_uri) as checkpointer:
    await checkpointer.setup()  # 创建所有必要的表结构
```

**`setup()` 方法执行的操作**：
1. 检查表是否存在
2. 如果不存在，创建所有表（checkpoints, checkpoint_writes, checkpoint_blobs, checkpoint_migrations）
3. 创建必要的索引
4. 记录迁移版本

#### 3.1.2 长期记忆初始化

```python
# 02_longTermTest.py
from langgraph.store.postgres import AsyncPostgresStore

async with AsyncPostgresStore.from_conn_string(db_uri) as store:
    await store.setup()  # 创建 store 和 store_migrations 表
```

### 3.2 数据写入流程

#### 3.2.1 Agent 执行时的数据写入

当调用 `agent.ainvoke()` 时：

```python
config = {"configurable": {"thread_id": "1"}}
agent_response = await agent.ainvoke(
    {"messages": [HumanMessage(content="预定一个汉庭酒店")]}, 
    config
)
```

**内部执行流程**：

1. **创建检查点**：
   - 生成新的 `checkpoint_id`（UUID）
   - 在 `checkpoints` 表中插入记录
   - 设置 `parent_checkpoint_id` 指向上一个检查点

2. **序列化消息**：
   - 将消息列表（HumanMessage, AIMessage, ToolMessage等）序列化为 msgpack 格式
   - 序列化后的二进制数据存储在 `checkpoint_writes` 表的 `blob` 字段中

3. **写入检查点数据**：
   - 在 `checkpoint_writes` 表中插入记录
   - `channel` 字段设置为 "messages"
   - `type` 字段设置为 "msgpack"
   - `blob` 字段存储序列化后的消息数据

4. **保存其他状态**：
   - 如果有 `pre_model_hook`，还会保存修剪后的消息到 `llm_input_messages` channel
   - 保存分支信息到 `branch:to:agent` 等 channel

#### 3.2.2 检查点链的形成

```
检查点链示例：
checkpoint_id: "1f0b944b-831e-6d7e-800e-a4cb9f31a179"
    └─ parent: "1f0b944b-5418-6516-800d-a529cec20dae"
        └─ parent: "1f0b944b-5415-60c8-800c-404df51f8d09"
            └─ parent: "1f0b944b-5414-65e2-800b-26090e81bd9b"
```

每次调用都会创建新的检查点，通过 `parent_checkpoint_id` 链接形成历史链。

### 3.3 数据读取流程

#### 3.3.1 通过 Agent 读取状态

```python
# query_chat_history.py
state = await agent.aget_state(config)
messages = state.values.get('messages', [])
```

**内部执行流程**：

1. **查找最新检查点**：
   - 根据 `thread_id` 在 `checkpoints` 表中查找最新的检查点
   - 使用 `checkpoint_id` 的最大值或时间戳

2. **读取二进制数据**：
   - 从 `checkpoint_writes` 表中读取 `channel = 'messages'` 的记录
   - 获取 `blob` 字段中的二进制数据

3. **反序列化数据**：
   - 将 msgpack 格式的二进制数据反序列化为消息对象
   - 恢复为 HumanMessage, AIMessage, ToolMessage 等对象

4. **返回状态**：
   - 返回包含所有消息的状态对象

#### 3.3.2 直接查询数据库的限制

**为什么 `query_chat_history.py` 无法直接看到表结构？**

1. **数据是二进制格式**：
   - `checkpoint_writes.blob` 字段存储的是 msgpack 序列化的二进制数据
   - 直接查询 SQL 只能看到二进制字节，无法直接阅读

2. **需要反序列化**：
   - 必须使用 LangGraph 的 API 来读取和反序列化数据
   - 消息对象包含复杂的元数据（工具调用、消息ID等）

3. **数据分散存储**：
   - 元数据在 `checkpoints` 表
   - 实际数据在 `checkpoint_writes` 表
   - 需要关联查询才能获取完整信息

**正确的查询方式**：

```python
# 方式1：通过 Agent API（推荐）
state = await agent.aget_state(config)
messages = state.values.get('messages', [])

# 方式2：通过 Checkpointer API
state_result = await checkpointer.aget_tuple(config)
# 然后反序列化 blob 数据
```

### 3.4 长期记忆的存储和检索

#### 3.4.1 存储长期记忆

```python
# 02_longTermTest.py
namespace = ("memories", config["configurable"]["user_id"])
memory1 = "我的名字叫南哥"
await store.aput(namespace, str(uuid.uuid4()), {"data": memory1})
```

**执行流程**：
1. `prefix` 设置为 "memories"
2. `key` 设置为 UUID
3. `value` 设置为 JSON 格式的数据
4. 插入到 `store` 表

#### 3.4.2 检索长期记忆

```python
# 02_longTermTest.py
namespace = ("memories", user_id)
memories = await store.asearch(namespace, query="")
info = " ".join([d.value["data"] for d in memories]) if memories else "无长期记忆信息"
```

**执行流程**：
1. 根据 `prefix` 在 `store` 表中查询
2. 返回匹配的 JSONB 数据
3. 支持向量搜索（如果配置了向量数据库）

## 六、关键要点总结

### 6.1 为什么看不到表结构？

1. **数据是二进制格式**：`checkpoint_writes.blob` 存储的是 msgpack 序列化的二进制数据
2. **需要反序列化**：必须使用 LangGraph API 才能读取和解析
3. **数据分散**：元数据在 `checkpoints`，实际数据在 `checkpoint_writes`

### 6.2 数据管理机制

1. **自动管理**：通过 `checkpointer.setup()` 自动创建表结构
2. **链式存储**：通过 `parent_checkpoint_id` 形成检查点链
3. **版本控制**：通过 `checkpoint_migrations` 管理schema版本
4. **会话隔离**：通过 `thread_id` 区分不同的对话会话

### 6.3 最佳实践

1. **使用 Agent API**：不要直接查询数据库，使用 `agent.aget_state()` 读取状态
2. **管理 thread_id**：为不同的会话使用不同的 `thread_id`
3. **定期清理**：可以定期清理旧的检查点数据
4. **监控存储**：监控 `checkpoint_writes` 表的 `blob` 大小，避免过大

## 七、SQL 查询示例

虽然不建议直接查询，但了解SQL结构有助于理解：

```sql
-- 查看所有会话
SELECT DISTINCT thread_id, COUNT(*) as checkpoint_count
FROM checkpoints
GROUP BY thread_id;

-- 查看某个会话的所有检查点
SELECT checkpoint_id, parent_checkpoint_id, created_at
FROM checkpoints
WHERE thread_id = '1'
ORDER BY checkpoint_id DESC;

-- 查看消息数据大小
SELECT thread_id, checkpoint_id, channel, length(blob) as blob_size
FROM checkpoint_writes
WHERE thread_id = '1' AND channel = 'messages'
ORDER BY checkpoint_id DESC;

-- 查看长期记忆
SELECT prefix, key, value, created_at
FROM store
WHERE prefix = 'memories'
ORDER BY created_at DESC;
```

## 八、总结

LangGraph 的数据库存储机制采用了**检查点模式**，通过以下方式实现：

1. **分层存储**：元数据在 `checkpoints`，实际数据在 `checkpoint_writes`
2. **二进制序列化**：使用 msgpack 格式高效存储消息对象
3. **链式结构**：通过父子关系形成检查点链，支持状态回溯
4. **自动管理**：通过 API 自动处理序列化/反序列化，简化使用

这就是为什么 `query_chat_history.py` 需要创建 Agent 并通过 API 读取数据，而不是直接查询数据库的原因。
